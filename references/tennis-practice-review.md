# 视频类型:网球练习复盘 (tennis practice review)

用户自己打球的实拍视频 → 教练视角分析不足 → 本地统一版式封面 → 总结式文案 → 统一收尾流程。
定型于 2026-08-17(拉球复盘 B 段,双平台定时发布)。

**与常规人物专题的根本区别:主角是用户本人,素材是他自己的整段实拍,没有身份核查问题,
也不做逐分解说口播。** 这条线不要套用「网球故事」的人物专题模板。

---

## 1. 触发方式

用户说「发这种打球视频 / 复盘我的练习视频 / 把这段拉球发了」等,给的是**他自己的比赛或练习录像**
(常见来源:SwingVision 导出的 rally 剪辑,画面右上角带数据覆盖层和落点小地图)。

---

## 2. 分析阶段 — 出教练结论

### 2.1 能自动读到的信息

SwingVision 素材的右上角有**逐拍信息框**(球种 + 球速)和**落点小地图**。用帧差扫描信息框区域
就能拿到整段的击球时间线,比人眼逐帧快得多:

```python
# 10Hz 扫描 (1420,370)-(1920,480) 区域的帧间差, 差值突变 = 新的一拍
# 输出每拍的时间戳, 再把该区域截图拼版 Read 一次即可读全部球种/球速
```

- 空白框 = 回合间隙,用来切分回合(4 个发球 + 3 个间隙 = 4 分)。
- 拍数统计要**扣掉空白帧**(2026-08-17 实测:62 个事件 - 3 个间隙 = 59 拍)。

### 2.2 ⚠ 回合结局**必须问用户**,不要自己从小地图推断

2026-08-17 的教训:靠落点小地图(实心=界内,空心=出界/下网)推断结局,3 分里错了 2 分 ——
把「对手打了记很深的底线球、用户够到但球弹出界」误判成用户主动打飞;把「切削没切好被吊高球、
伸手没截到」误判成用户主动降档失误。**这类信息画面里根本没有,只有当事人知道。**

正确做法:先给出每一分的**技术观察**(击球质量、站位、动作),把**结局判定留给用户确认**,
用户口述之后再据此改写分析。

### 2.3 技术动作看哪里

用 video-autoreframe 的检测结果定位人物,按人物中心裁 520×520 抽「引拍 / 触球 / 随挥」三帧看:

- **双反**:引拍转肩到位但触球点偏后偏近身、重心留后脚、前脚横着没踩进去 → 典型的回球又浅又软
- **正手**:开放式站位、外侧腿蓄力、击球点在体前、转体带跳 = 好球的样子
- **中前场/被动球**:正面硬够、全幅引拍来不及、手腕捞球 = 缺预案

## 3. 封面 — 本地渲染,不要用 GPT 生成

**用户 2026-08-17 明确否决了 GPT 生成封面**:GPT 会把画面重绘,**把对手裁掉、人物变成"像他的
另一个人"**。这条线的封面一律 `scripts/make_covers_practice.py` 本地拼接。

### 3.1 底图选帧 — 用户指定的三种瞬间

只能用这三种动作帧之一(用户 2026-08-17 定):

1. **正手拉拍准备击球**(引拍到位、球在画面中、非持拍手指向来球)← 最推荐
2. **反手拉拍准备击球**
3. **发球击球一瞬间**

选帧硬条件:

- 人物**离镜头近**(检测 bbox 高度 ≥ 380px 为佳)
- **对手要在画面里**(用户明确不接受把对手裁掉的构图)
- 人物**头顶有留白**(天花板/看台)给标题落位
- **避开 SwingVision 覆盖层**:数据框和小地图在右上角约 x≥1420,竖版 3:4 裁切时人物 x 落在
  0.42–0.62W 最安全;横版 4:3 用 `--bias-h 0` 把右边整条排除

选帧脚本口径:先用检测结果筛出「击球事件前 0.3s 且人物居中偏大」的候选,拼版 Read 一次挑定。

### 3.2 版式规格(逐像素量自用户认可的稿子,已冻结)

| 元素 | 规格 |
|---|---|
| 画布 | 竖 3:4 `1242×1656` / 横 4:3 `1440×1080`,两版各自取景,**不互相裁切** |
| 顶部压暗 | 线性渐变,强度 205,向下淡出到 0.52H |
| 胶囊 | 左上角实心圆角矩形,`#781F15`,x=.028W y=.032H h=.057H,圆角=.30h,白字 Songti Bold(.52h) |
| 胶囊文字 | **视频类型**,本类型固定为 **「网球练习」**(用户 2026-08-17:这类视频不叫「网球故事」) |
| 主标题 | Songti SC Black(Songti.ttc index 0),白字 + `#2D2D2C` 描边,顶边 y=.113H,字高 .137H,**自动缩到 ≤.94W** |
| 副标题 | Songti SC Bold,金色 `#F9E093`,顶边 y=.259H,字高 .052H,**不画分隔线** |

```bash
python3 <skill>/scripts/make_covers_practice.py \
  --video 源.mp4 --t 93.3 \
  --title "练习 vs UTR 6+" --sub "复盘提高" --tag "网球练习" \
  --outdir final/covers/ --bias-v 0.51 --bias-h 0.0
```

⚠ 标题字号是**自适应**的:写死字号时长标题(如「练习 vs UTR 6+」)会被静默画出画面外、首尾字
被裁掉。`publish-xhs-douyin/scripts/make_covers.py` 的同一个缺陷已于 2026-08-17 一并修掉。

## 4. 文案 — 总结式,不逐分复述

用户 2026-08-17 连提两条硬要求:

1. **「不用说那么多,只需要用总结的方式大概说一下问题在哪、该怎么解决就行」**
2. **「删掉『几分多少拍』还有球速的描述,这些没有意义」**

所以结构固定为:

```
一句话交代对手水平/场景
  ↓
赢下来的分靠什么(一两句带过)
  ↓
3 个问题,每个写成「问题现象」+「怎么改」两行
  ↓
做得还可以的一句
  ↓
开放式提问收尾
```

**禁止出现**:`X分X拍`、`XX公里/小时`、任何 SwingVision 球速数字、逐分流水账。
问题描述改用体感语言(「回球又浅又软」而不是「反手只有44」)。

长度:小红书约 400 字(保留分行),抖音约 350 字(简介里回车不生成换行,连排单段)。

标题:`🎾` 前缀 + 用户的系列命名习惯(如 `🎾练习 vs UTR 6+，复盘提高`);XHS ≤20 字、抖音 ≤30 字。
封面主标可以是标题的前半段,副标是后半段。

## 5. 成片收尾 — 统一流程

本类型**不做逐分解说口播**(用户 2026-08-17:「先别根据视频生成口播了」),但收尾流程照旧:

```bash
# 在 CRF 12 母版上做, 不要在压缩版上二次编码
python3 <skill>/scripts/finalize_ending.py final/<成片>.mp4
```

`finalize_ending.py` 一步完成三件事:**升格 1080p 60fps** + 追加**品牌片尾** `ending.mov` +
混入**片尾语音** `ending_voice.wav`(关注引导)。产物带 `finalized-with-ending` 标记,幂等。

核验:`ffprobe` 读回 `r_frame_rate=60/1`、时长 = 正片 + 片尾长度、抽尾帧确认品牌卡在位。

上传版另压一份(CRF 21 约 0.5MB/s),母版保留。

## 7. 这条线上踩过的坑(别重犯)

1. **别拿一个站点的行为推广到所有站点。** 2026-08-17 我在 chatgpt.com 上测 window.name 接力被
   清空(ChatGPT 设了 COOP),就断言「Chrome 会清空 window.name,大视频传不进去」,让用户白等一轮
   并差点让他手动拖文件。实测:**creator.xiaohongshu.com 和 creator.douyin.com 都完整保留
   window.name**(76,100,148 字符原样过来)。任何"做不到"的结论,必须在**目标站点本身**上验证。
2. **没读回验证就不许说"已完成"。** 同一天我说「两个平台都在传了」,实际小红书的注入压根没跑、
   抖音我把常驻的「重新上传」按钮误判成失败标记。判定上传成功的正确口径:抖音看
   `上传成功` 字样 + 视频预览元素;小红书看 `重新上传 <文件名>` + `检测为高清视频`。
3. **封面版式要先对齐账号既有标准再动手**,不要拿通用脚本的默认样式交付(第一版本地封面的
   字体/颜色/位置全不对,返工两轮)。
